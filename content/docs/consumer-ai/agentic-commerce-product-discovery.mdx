# Agentic Commerce Product Discovery Layer

一句话判断：AI 购物 agent 不是缺“会聊天的导购”，而是缺一个能被 agent 稳定调用、可核验、可购买、可解释的商品发现层。

今天的商品信息主要为人类页面、搜索引擎和广告系统设计。用户问的是“预算 8000 以内，适合剪视频和轻游戏的笔记本，别太重，今天能买到”，但底层商品数据往往分散在商家页面、比价站、库存接口、评论区和平台搜索里。普通聊天框能给建议，却很难保证价格、库存、购买链接、替代品和商家规则都是真的。

这个缺口会变成创业机会：给购物 agent、生活 agent、内容平台、垂直导购和商家工具提供一层 agent-native product graph。

## 赛道 / 产品信号

几个公开信号集中指向同一件事：商品发现正在被改造成 agent 可调用能力。

- HN 在 2026-05-15 出现 Seekon 的 Show HN：标题就是 “Agentic product discovery for AI apps and shopping agents”。热度不高，4 points / 0 comments，但方向很直。
- Seekon 开发者页把自己定位成 “Product Intelligence Developers”，提供 MCP Server、API、agentic catalog intelligence、实时库存和价格同步、商品图片、商家购买链接。免费层是 100 次 MCP tool calls / day。
- AskUCP 页面把自己称为 “AI-native shopping search”，说明目标是用 Universal Commerce Protocol 搜索 Shopify 生态及更多商品。
- GitHub 上已经出现一批低热但很具体的 agentic commerce 项目：Agorio SDK、Upsonic UCP-Agent、UK Grocery CLI、Nexscope eCommerce Skills。它们不是“泛 AI 助手”，而是围绕商品搜索、购物车、折扣、地址、支付、marketplace seller 工作流这些具体动作。

信号还早。正因为早，适合看创业楔子，而不是等大平台把协议和接口全定死。

## 用户痛点

### C 端用户

用户不缺商品页面，缺的是判断。

- 同一个需求会横跨预算、品牌、库存、配送、售后、优惠、兼容性、真实评价。
- 搜索结果和推荐流夹着广告，用户不知道哪个是“适合我”，哪个只是“投放更猛”。
- 大件、数码、母婴、营养品、旅行装备、企业采购这类品类决策成本高。用户愿意让 AI 做 shortlist，但不敢让它直接乱买。
- 购物 agent 如果只能“推荐几个商品名”，价值不够；如果能给证据、替代、购买路径和风险提示，用户才会回来。

### 商家 / 平台 / 开发者

商家的痛点更商业化：未来用户入口可能不是站内搜索框，而是 AI agent。

- 商家页面现在面向 SEO、广告和人类浏览，不一定适合 agent 抓取和比较。
- 实时价格、库存、sku、运费、优惠、退换货规则很难被聊天模型稳定理解。
- AI agent 给出的商品推荐如果没有标准化数据和可追踪 purchase link，商家很难归因，也很难优化。
- 开发者要做购物 agent，需要商品 catalog、merchant discovery、cart、checkout、receipt、user consent，一套都自己爬很脏。

## AI-native wedge

不要做“AI 导购 App”。那太宽，也太容易被平台搜索吃掉。

更好的 wedge 是：

> 开发者给一句购买意图和约束；系统返回可被 agent 调用的商品 shortlist，包括价格、库存、商家链接、关键属性、风险提示、替代品和可审计的购买前确认卡。

第一版可以只做一个垂直品类，比如：

- 英国超市购物 agent：多超市搜索、购物篮、配送时间、价格替代。
- 数码 / PC 配置导购：把需求压成配置约束、商品 shortlist、兼容性和售后风险。
- Shopify / DTC 商品 agent feed：帮独立站把商品包装成 agent 可读、可搜索、可购买的 catalog。
- 企业采购小额物品：办公设备、开发板、耗材，用审批卡和采购 receipt 控制风险。

关键不是“聊天”，而是把模糊意图压成购买判断。

## 为什么现在热

1. **Agent 开始真的接工具。** MCP、tool calling、browser agent、mobile agent 让购物不再停在文本建议，可以进入搜索、比价、加购、下单前确认。
2. **商品数据不为 agent 准备。** 商品页面给人看，API 给平台内用，agent 需要的是属性化、实时化、可验证、可执行的数据。
3. **协议和 SDK 开始冒头。** Agorio README 明确讲 UCP / ACP；Upsonic UCP-Agent 展示了 product、cart、discount、address、purchase 等工具调用形态。
4. **平台入口会变。** 用户会越来越常问 AI “帮我买 / 帮我选 / 帮我比较”。能被 agent 正确读取的商品，有机会获得新的分发。
5. **商家会关心归因。** 如果 AI shopping agent 带来订单，商家需要知道哪个 agent、哪个 prompt、哪个商品属性触发了购买。

## 用户为什么来 / 留 / 传播 / 付费

### 为什么来

用户来，是因为普通搜索把判断成本丢给他。一个好的购物 agent 可以直接给：

- 三个候选商品。
- 每个商品为什么适合。
- 当前价格和库存。
- 不推荐哪些商品，原因是什么。
- 下单前需要人工确认的风险点。

### 为什么留

用户会留在“历史偏好 + 风险偏好 + 家庭/公司约束”里。

比如同一个人可能长期偏好轻量、保修强、少折腾；同一个家庭可能有过敏、儿童、宠物、配送时间约束；同一个公司可能有采购价格线、发票、审批和供应商要求。这些记忆让 agent 下次更快。

### 为什么传播

可传播的不是产品首页，而是购买判断卡：

- `我让 agent 比了 6 款显示器，最后排除了 2 款虚标亮度的。`
- `这个 grocery agent 帮我把 Tesco / Sainsbury's / Ocado 同一周菜单凑齐，还给了替代品。`
- `给爸妈买手机的 shortlist，带了风险和售后解释。`

用户会转发的是“省了我一次纠结”的卡片。

### 谁付费

- 开发者：为商品 API、catalog search、tool calls、checkout sandbox 付费。
- 商家：为 agent-readable feed、商品属性修复、购买归因、转化分析付费。
- 垂直导购团队：为品类知识、库存价格、评测证据和 referral link 管理付费。
- 企业采购团队：为审批、receipt、合规记录和供应商规则付费。

C 端订阅也能做，但最好不要第一天押 C 端订阅。更稳的第一笔钱来自 B2B / developer / merchant。

## MVP 实验

### MVP 1：垂直商品判断 API

选一个低合规、高频、信息脏的品类。比如办公显示器、开发者电脑、咖啡器具、宠物用品、英国超市购物。

输入：自然语言需求。

输出：

- 商品 shortlist。
- 每个商品的属性证据。
- 当前价格 / 库存 /购买链接。
- 排除项。
- 购买前确认卡。

验证：20 个真实用户任务，比较“普通搜索 / ChatGPT 建议 / 本产品”的决策时间、满意度、退换货风险、最终购买率。

### MVP 2：Agent-readable merchant feed

找 20 个 Shopify / DTC 商家，帮他们生成 agent-readable catalog：

- 商品属性补全。
- 适合哪些 prompt。
- 不适合哪些用户。
- 库存价格同步。
- 可追踪购买链接。

验证：用一批固定购物 prompt 测试 AI agent 是否能更稳定地找到这些商品，并记录点击 / 加购 / 购买前确认。

### MVP 3：购物 agent 的下单前审批卡

不要一开始碰自动支付。先做下单前的确认层：

- 购买理由。
- 总价、运费、到货时间。
- 退换货规则。
- 替代品。
- 风险。
- 用户显式确认。

如果用户愿意在这个卡片上点确认，说明信任开始成立。

## 商业化路径

1. 免费 API / MCP server：限制 tool calls，吸引 agent builder。
2. Developer Pro：更高调用量、更多品类、稳定 SLA、sandbox checkout。
3. Merchant Pro：商品 feed 修复、agent visibility、购买归因、A/B prompt 测试。
4. Vertical Pack：针对数码、超市、母婴、宠物、企业采购做品类数据和评测模板。
5. Enterprise：审批、审计、采购规则、SSO、私有商品库、供应商白名单。

这里的付费点不是“AI 推荐”，而是可信商品数据、可执行购买路径和可追踪归因。

## 反例 / 风险

1. **平台会拦。** Amazon、淘宝、京东、Shopify、Google、OpenAI、Stripe 都有理由把 agentic commerce 的关键入口抓在自己手里。
2. **自动下单信任门槛很高。** 用户可能愿意让 AI 比较商品，但不愿让它直接付款。必须先做人类确认。
3. **商品数据很脏。** SKU、价格、库存、优惠、地区配送、退换货规则都会变。数据不准一次，信任掉一大截。
4. **推荐容易被商业化污染。** 一旦 referral / sponsored 商品进入排序，必须清楚标注，否则用户会把它当广告。
5. **品类知识很重。** 数码、食品、母婴、药品、保险、金融产品的风险完全不同，不能用一套泛化逻辑硬套。
6. **法规和责任不轻。** 金融、医疗、营养、儿童用品等品类不能只靠模型建议。要有风险边界。

## 可验证指标

- 从输入需求到 shortlist 的时间是否低于 30 秒。
- 用户是否点击至少一个购买链接。
- 用户是否认为“不推荐理由”可信。
- 商品价格 / 库存错误率。
- 购买前确认卡的确认率。
- 同一用户 30 天内是否回来做第二次购买判断。
- 商家侧 agent-driven click / add-to-cart / purchase 是否可归因。
- agent 对同一需求多次运行的结果稳定性。

## 结论

Agentic commerce 的真机会不是做一个漂亮购物聊天框，而是做商品判断的基础层。

如果未来用户把“帮我选、帮我买、帮我比较”交给 agent，那么商品世界需要新的接口：商品不仅要被人看见，也要被 agent 理解、比较、验证和安全执行。

早期创业切口应该避开全平台大而全，先选一个高痛品类，把“模糊购买意图 → 可信 shortlist → 下单前确认卡”跑通。
