# Local LLM Hardware Fit Layer

## 一句话判断

本地 LLM 的痛点不是再多一个模型榜单，而是判断某台真实机器上哪个模型跑得动、跑得快、质量够用，并把这个判断变成可复测的配置。

这个方向比“本地大模型管理器”更窄，也更像早期刚需。用户不是缺模型名字，而是怕下载 30GB 之后发现慢、炸显存、回答还不如更小的新模型。

## 赛道 / 产品信号

本轮信号集中在本地模型选择和硬件适配：

- whichllm 在 HN 以 “Find the best local LLM for your hardware” 出现，HN 信号是 277 points、63 comments。GitHub 描述很明确：自动检测 GPU / CPU / RAM，按真实、近期 benchmark 排序，而不是按参数量排序。
- whichllm README 给的例子很扎实：同一张 RTX 4090 上，32B 模型虽然能跑，但 27B 新一代模型可能因为真实 benchmark 更好而排第一。这正是普通用户最难判断的点。
- Anubis OSS 是 Apple Silicon 本地 LLM benchmark 工具，README 写到支持 Ollama、MLX、LM Studio Server、OpenWebUI、Docker Models 等 OpenAI-compatible endpoint，并有 375+ community submitted runs 分析。
- 近期 HN 里还有 “I tested 8 LLM models on Linux without using the GPU” 这类内容，说明本地模型选择已经从少数发烧友扩散到普通开发者和 AI power user。

判断：本地 LLM 会从“能不能跑”进入“针对我的机器和任务，哪个模型最值得跑”。这里会长出一层硬件适配、benchmark、配置推荐和任务路由工具。

## 用户痛点是什么

真实用户的问题很具体：

1. **模型太多，硬件差异太大。** 同一个模型在 8GB Mac、16GB Mac、RTX 3060、RTX 4090、CPU-only Linux 上体验完全不同。
2. **参数量误导严重。** 大模型不一定更适合当前机器。新一代小模型、量化格式、上下文长度、token/s、显存余量都影响实际可用性。
3. **下载和试错成本高。** 用户要装 Ollama / LM Studio / MLX，下载多个模型，跑 prompt，再自己比较速度和质量。
4. **任务没有被纳入判断。** 写代码、总结文档、中文问答、结构化抽取、长上下文阅读，对模型的要求不同。单一 benchmark 排名不够。
5. **配置不可复现。** 今天能跑的组合，换驱动、换后端、换量化版本后可能变慢或变差。团队没法把“可用配置”沉淀下来。

真正痛点是：用户缺一个面向具体硬件和具体任务的模型选择判断层。

## AI-native wedge

最小 wedge：

**用户运行一个本地诊断命令；系统检测硬件和已安装后端，拉取近期公开 benchmark，跑 3 个短任务校准，然后输出“推荐模型 + 量化格式 + 运行后端 + 任务路由配置”。**

第一版可以只做开发者和 AI power user：

```bash
llmfit diagnose
llmfit recommend --task coding,rag,zh-summary --budget 16gb
llmfit run-card --export llmfit.yaml
```

输出不是一张泛榜单，而是一张可执行 run card：

```yaml
machine: macbook-m4-16gb
backend: mlx
routes:
  coding-small-edit: qwen3-coder-7b-q4
  chinese-summary: qwen3-8b-q5
  long-context-rag: llama-3.2-3b-q8
notes:
  - avoid 32b on this machine for interactive work
  - rerun benchmark after backend upgrade
```

AI 压缩的不是“搜索模型信息”。它压缩的是“硬件检测、模型筛选、任务试跑、质量速度权衡、配置落盘”这一串判断。

## 为什么现在

- 本地 LLM 的供给过剩了。Hugging Face、Ollama、MLX、LM Studio、OpenWebUI 让模型获取变简单，但选择成本反而上升。
- 端侧硬件差异拉大。Apple Silicon、消费级 NVIDIA GPU、mini PC、CPU-only 环境都有用户，但统一榜单无法回答个体问题。
- 隐私和成本把用户推向本地运行。代码、笔记、客户资料、公司文档不一定适合直接丢给云模型。
- 小模型进步快。只看参数量会错过“更小但更适合当前任务”的模型。
- AI coding、个人知识库、本地自动化正在把本地模型从玩具推向日常工具。日常工具需要稳定配置，而不是每周重试一次。

## 用户为什么来 / 留 / 传播 / 付费

**为什么来：**

用户刚买机器、刚装 Ollama / LM Studio，或者被一个模型推荐帖劝下载后发现跑不动。他要的是“我的机器到底该跑哪个”。

**为什么留：**

模型和后端持续更新。每次新模型发布、驱动升级、硬件变化后，用户都需要重新生成 run card。团队还会积累自己的任务 benchmark。

**为什么传播：**

最容易传播的是硬件适配卡：

```md
M4 16GB local LLM card
Best interactive coding: qwen3-coder-7b-q4, 41 tok/s
Best Chinese summary: qwen3-8b-q5, 36 tok/s
Avoid: 32B q4 for chat, memory pressure too high
```

这类卡片比“我在用某某模型”更有参考价值，因为它绑定了硬件、任务和实测结果。

**谁付费：**

- AI power user：为私有数据、本地速度和硬件购买决策付费。
- 小团队：为统一本地模型配置、共享 benchmark、CI / agent 本地后端选择付费。
- 企业 IT / 安全部门：为离线部署评估、设备选型、模型白名单、可审计 run card 付费。
- 硬件卖家 / 本地 AI 设备厂商：为可验证的设备模型适配报告付费，但这条路要小心中立性。

## MVP 实验

### 7 天 MVP

做一个只支持 macOS + Ollama / MLX 的 CLI：

1. 检测芯片、内存、可用后端、已安装模型。
2. 读取公开 model card 和 benchmark 元数据。
3. 自动下载 2-3 个候选小模型，跑固定短任务：中文摘要、代码解释、JSON 抽取。
4. 输出速度、内存占用、任务质量人工评分入口。
5. 生成 `llmfit.yaml`。

先不做模型托管，不做社区平台，不做聊天界面。只验证用户是否愿意按推荐配置真实使用。

### 30 天验证

- 找 30 个本地 LLM 用户，覆盖 8GB / 16GB / 32GB Mac、消费级 NVIDIA GPU、CPU-only Linux。
- 让他们先按自己的方法选模型，再用工具推荐模型。
- 对比首次可用时间、下载浪费、交互延迟、7 天后仍在使用的模型。
- 观察用户是否愿意分享硬件适配卡，是否愿意为历史 run card 和团队配置同步付费。

## 可验证指标

- 从安装到得到可用模型配置的时间。
- 被工具推荐后，用户实际保留使用的比例。
- 错误推荐率：跑不动、慢到不可用、质量明显不达标。
- 下载浪费减少量：无效模型下载 GB 数。
- 同一硬件上推荐结果的可复现性。
- 用户是否愿意分享硬件适配卡。
- 团队是否把 run card 纳入 agent / RAG / 本地工作流配置。

## 商业化路径

1. **免费 CLI。** 先做本地检测、公开 benchmark 聚合、run card 生成。
2. **社区硬件榜。** 用户可匿名上传硬件、后端、模型、任务结果。默认脱敏，不上传 prompt 内容。
3. **任务包。** 面向 coding、RAG、中文办公、客服摘要、法务检索等任务提供专用测试集。
4. **团队版。** 共享 run card、模型白名单、后端版本锁定、设备选型报告。
5. **企业私有评估。** 在离线环境里跑模型适配和安全检查，输出采购和部署建议。

## 反例 / 风险

1. **开源工具可能吃掉基础需求。** whichllm、Anubis、Ollama、LM Studio 都可能继续补齐推荐能力。创业机会要从“榜单”升级到“任务 + 硬件 + 团队配置”。
2. **benchmark 容易失真。** 小样本任务和真实长期使用不同。必须让用户加入自己的任务集。
3. **模型更新太快。** 数据过期会伤信任。需要 recency-aware，而不是静态榜单。
4. **隐私边界要硬。** 本地 prompt、文件名、代码片段不能默认上传。社区榜只上传硬件和匿名统计。
5. **付费意愿可能偏弱。** 个人用户可能只用一次。更强的付费点在团队 run card、设备选型和私有部署评估。
6. **硬件厂商合作会污染判断。** 如果推荐被商业赞助影响，产品会立刻失去可信度。

## 创业判断

这个方向值得追，因为它站在本地 AI 普及的第一个真实坑上：不是人人都会训练模型，但越来越多人会问“我这台机器到底能跑什么”。

最好的早期产品不是模型商店，也不是聊天壳。是一个本地诊断 + 任务试跑 + 可复现 run card 的判断层。

如果它能把本地模型试错从半天压到十分钟，且推荐结果一周后仍被用户保留，就有机会从开源 CLI 长成团队级本地 AI 配置平台。
