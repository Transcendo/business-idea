# Mobile AI Test Agent

## 一句话判断

移动 App QA 的机会不是再写更多 Appium 脚本，而是把自然语言用例、屏幕观察、动作执行、失败修复和证据报告压成可复跑的测试 agent。

这不是通用手机助手。更窄，也更能收钱：当 AI coding agent 和低代码工具把移动端迭代速度拉快后，团队最先痛的是“新功能生成了，但我不敢发版”。

## 赛道 / 产品信号

本轮信号集中在 mobile QA agent：

- Product Hunt 上 Drizz 的定位很直接：`Mobile tests that write, run, and fix themselves`。这说明移动测试从“写脚本”转向“自动生成、运行、修复”。
- GitHub 上 FinalRun 把自己定义成 AI-driven CLI，用自然语言 YAML 测 Android / iOS App。它会在模拟器或真机环境中看屏幕、点击、滑动、输入，并输出 pass/fail report、视频和设备日志。
- HN 过去已经出现 CamelQA、GPT Driver、Agent-QA、App Use 等移动/端到端测试讨论。移动端测试不是新需求，但 AI 让“写测试”和“维护测试”这两步可以被重新拆。
- GitHub 搜索里已经出现一批低 star 的 mobile self-healing test agent 原型。早期项目很糙，恰好说明需求正在从团队内部脚本冒出来。
- Reddit 本轮抓取被 403 挡住，但上一轮候选池已经记录 ChatGPTCoding 里开发者抱怨 AI coding 工具最容易掉在测试、复现和验收步骤。这是需求侧信号，不是供应侧自嗨。

判断：这个方向比“移动 GUI agent runtime”更适合先商业化。runtime 是底层能力，mobile AI test agent 是明确购买场景。

## 用户痛点是什么

移动团队不是缺一个会聊天的测试机器人。痛点是：

1. **测试脚本跟不上生成速度。** AI coding / app builder 让功能改得更快，但 QA 脚本仍然靠人补。
2. **移动 UI 太脆。** WebView、Flutter、React Native、系统弹窗、权限窗、键盘、弱网、横竖屏都会让传统脚本断。
3. **失败证据不够。** 只报 `failed` 没用，工程师需要看到视频、截图、设备日志、最后一次动作和断言依据。
4. **维护成本吞掉 ROI。** 自动化测试最贵的不是第一次写，是每次 UI 变动后修。
5. **AI 生成 App 更需要发布闸门。** 越是 vibe coding，越需要独立 QA agent 证明核心流程没炸。

## AI-native wedge

最小 wedge：

**用户给 App 包、测试账号和自然语言验收目标；系统返回可复跑的移动测试用例、执行视频、失败定位、修复建议和 release-ready receipt。**

第一版不要做万能测试平台。只压缩三件事：

- 从 PR / user story / Figma / README 生成移动测试 YAML。
- 在 Android emulator / iOS simulator / 云真机上执行屏幕动作。
- 失败后生成证据包：截图、视频、日志、最后动作、可能原因、下一次修复建议。

AI 真正压缩的不是“点按钮”，而是把自然语言验收标准变成可运行、可复查、可分享的测试资产。

## 为什么现在

- 多模态模型能读移动屏幕，按钮识别、状态判断、文案断言都比过去更可用。
- AI coding agent 正在推高发版频率，测试会成为新瓶颈。
- 移动端没有网页自动化那么统一。Appium 能打底，但自然语言生成、视觉判断、失败修复更适合 AI。
- 云设备、模拟器、CI 已经成熟，缺的是 AI-native 的用例生成、执行解释和证据报告。
- HN、Product Hunt、GitHub 上已经同时出现供应侧产品和开发者讨论，说明窗口不是单点噪声。

## 用户为什么来 / 留 / 传播 / 付费

**为什么来：**
移动团队刚用 AI 写完功能，但没有足够 QA 人力补测试。最直接入口是“帮我测这个 PR 的 5 条核心路径”。

**为什么留：**
一旦测试用例进 CI，每次发版都会跑。失败证据、用例修复、历史回放和 flaky test 归因会形成持续价值。

**为什么传播：**
传播单元是测试 receipt：

- `登录、搜索、下单、支付前确认 4 条路径已在 3 台设备跑过。`
- `本次失败发生在 iOS 17.5 的系统权限弹窗后，Android 正常。`
- `AI 生成的注册页改动导致第 6 步按钮不可点击，附视频和日志。`

这种卡片能被转进 GitHub PR、Linear、飞书群、QA 群。

**谁付费：**
移动 App 团队、AI app builder、外包交付团队、出海工具团队、游戏之外的高频发版 App。收费按并发设备、测试分钟、项目数、CI seats、证据存储和私有部署收。

## MVP 实验

### 7 天 MVP

只做 Android，先别碰 iOS 复杂权限。

输入：

- APK 或 repo。
- 3 条自然语言用例。
- 测试账号或一次人工登录。

输出：

- 生成的 YAML 测试用例。
- 每条用例的执行视频。
- pass/fail 结果。
- 失败步骤截图和日志。
- 一段可贴进 PR 的 release receipt。

### 30 天验证

- 找 8 个移动 App 团队，每队只测一个核心流程。
- 让他们在真实 PR 上跑，不要用演示 App 糊弄自己。
- 记录人工写测试时间、首次跑通时间、失败定位时间、用例复用次数。
- 对比“AI 生成 + 人审”与“纯手写 Appium”的总时间。

## 可验证指标

- 从自然语言需求到第一条可运行测试的时间。
- 首次运行成功率。
- 失败报告能否让工程师在 10 分钟内定位问题。
- 同一用例跨 3 个版本的存活率。
- flaky test 占比。
- 每个 PR 节省的 QA 分钟数。
- receipt 被贴进 PR / issue 的比例。
- 用户是否愿意为第二个 App 或 CI 并发付费。

## 商业化路径

1. **CLI + GitHub Action。** 先进入开发者工作流，减少采购阻力。
2. **托管设备池。** 提供 Android emulator、iOS simulator、云真机、并发调度。
3. **证据报告。** 视频、截图、日志、失败分类、PR comment。
4. **自愈维护。** UI 文案或布局小改时自动提出修复 diff，人审后合入。
5. **企业版。** 私有部署、测试账号隔离、敏感步骤遮罩、审计日志。

## 反例 / 风险

1. **测试判断可能胡说。** 视觉模型会误判状态。必须有结构化断言和人工可复查证据。
2. **移动环境维护重。** 模拟器、真机、iOS 签名、权限、系统版本会拖慢小团队。
3. **大厂测试平台会下压。** BrowserStack、Sauce Labs、Firebase Test Lab、GitHub Actions 都可能加 AI。创业公司要先吃 AI-native 团队和新 App builder。
4. **只做 demo 没价值。** 如果不能接 CI、不能输出 PR receipt，就会沦为炫技视频。
5. **iOS 是坑。** 早期只做 Android 或模拟器，等需求验证后再扩。

## 后续跟踪点

- Drizz 是否能拿到移动团队真实用例，而不是停在 Product Hunt launch。
- FinalRun 这类 CLI 是否进入 GitHub Action / CI 工作流。
- 自愈修复到底是自动改测试，还是只给建议。
- 用户更愿意为“生成测试”付费，还是为“每次发版的证据报告”付费。
