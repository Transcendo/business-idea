# Agent-Readable Database Contract Layer

## 一句话判断

AI coding agent 正在从“改前端和业务函数”走向“改数据库 schema、写 migration、改查询层”。这里最危险的不是模型不会 SQL，而是它不知道当前数据库的真实 contract：哪些表和字段存在、哪些迁移已经落地、哪些查询会碰敏感字段、哪些变更会破坏生产数据。

机会不是再做一个 ORM。机会是做 agent-readable database contract layer：把 schema、迁移图、类型、查询计划、权限和 drift 状态压成机器可读的 contract，让 agent 在动数据库前先拿到可验证边界，动完后留下 contract receipt。

## 赛道 / 产品信号

Prisma Next 在 2026-05-22 上了 HN，标题是 “data contracts, migration graphs, agent DX”。GitHub 仓库把新架构写得很直白：从生成客户端转向 contract-first model，核心产物是 deterministic JSON contract、TypeScript types、contractHash、structured Plans、migration graph、hook/middleware。

它的 ARCHITECTURE 文档里有几个强信号：

- schema 不再只是 codegen 的输入，而是稳定、可版本化的数据 contract。
- contract 带 `contractHash`，把类型、查询计划和 schema 版本绑在一起。
- structured Plans 包含 AST、引用列和 contract hash，便于验证和 drift detection。
- migration 系统强调 graph，而不是线性脚本堆叠。
- hook framework 可以做 linting、telemetry、query budgets、policy enforcement。

HN 分数不高，13 points、2 comments。但评论也指出：完整 TypeScript 重写只是改进，最野心的是新的 migration system。这说明 builder 关注的不是“Prisma 换语言”，而是数据库 contract 能不能支撑下一代工具链。

判断：Prisma Next 是一个产品信号，不等于最终创业机会。真正更窄的机会在 Prisma、Drizzle、SQLAlchemy、Rails、Django、Supabase、Neon 之外：给 AI coding agent 提供跨框架的 database contract gate。

## 用户痛点是什么

1. **Agent 改 DB 很容易越界。** 它会根据代码猜 schema，但真实数据库可能已经 drift，或者线上 migration 状态和本地不一致。
2. **Migration review 太依赖人脑。** 人要检查字段删除、索引影响、数据回填、锁表风险、外键影响和回滚路径。
3. **ORM 生成物对 agent 不友好。** 生成客户端对人好用，但 agent 更需要结构化 contract、依赖图、风险说明和可验证 plan。
4. **多 agent 并行会制造 schema 冲突。** 两个 agent 同时改数据模型，普通 git conflict 看不出迁移图冲突。
5. **数据库权限和敏感字段缺少执行边界。** Agent 读写数据时，代码 review 很难确认它有没有碰不该碰的表和字段。

痛点不是“开发者不会写 SQL”。痛点是 agent 让数据库变更频率上升，但团队没有一个机器可读、可审查、可回放的数据库合约层。

## AI-native wedge

最小 wedge：

用户把 repo、数据库 schema、migration 文件和 agent PR 交给系统；系统生成一份 `db-contract.json`，再对 agent 的变更输出 `contract-diff receipt`。

这张 receipt 要回答：

- 本次变更引用了哪些表、字段、索引和约束。
- migration graph 是否和主分支冲突。
- 是否删除或重命名了被代码仍然引用的字段。
- 是否触碰敏感字段或高风险表。
- 查询 plan 是否突破预算，比如无索引扫描、N+1 风险、锁表风险。
- contractHash 是否和生成类型、测试环境、PR diff 一致。

AI 压缩的任务不是“自动写 migration”。它压缩的是从“agent 说它改好了”到“人能判断这次数据库变更能不能合”的整段审查、查证和复盘。

## 为什么现在热

- Coding agent 已经能批量改业务代码，下一层瓶颈自然落到数据库、auth、storage、queue 这些有状态系统。
- Prisma Next 把 contract-first、migration graph、agent DX 摆到台面上，说明数据库工具链正在为 agent 时代重构。
- OpenAI Codex、Claude Code、Cursor、OpenCode 这类工具让更多 PR 由 agent 发起。数据库 PR 会越来越多，也越来越难靠人工逐行看完。
- Postgres branching、schema introspection、AST 分析、query plan 解释、CI gate 都已经可用，缺的是把它们拼成 agent 审查产品。
- 企业买单点清楚：数据库事故贵，migration review 慢，agent PR 的信任成本高。

## 用户为什么来 / 留 / 传播 / 付费

### 为什么来

团队刚遇到过 agent 写错 migration、漏改 query、删字段导致测试没覆盖、或者本地 schema 和 staging 不一致。此时他们不是想听“模型会更强”，而是想要一个合并前能拦住 DB 风险的 gate。

### 为什么留

一旦 contract 接入 CI 和 PR review，每次数据库相关变更都会留下可比对的 contract diff。团队会逐渐形成习惯：没有 DB contract receipt 的 agent PR 不准合。

### 为什么传播

传播单元不是抽象架构图，而是 PR 里的短卡片：

```md
DB contract: 9f42c7
Migration graph: no conflict
Fields removed: 0
Sensitive fields touched: users.email read-only
Query budget: 2 warnings
Rollback: generated and tested
Reviewer action: approve after index confirmation
```

工程团队会转发这种卡片，因为它把“我看不懂 agent 到底动了什么”变成可讨论证据。

### 谁付费

AI-heavy SaaS 团队、内部平台团队、AI coding 平台、数据库平台、金融和医疗软件团队、AI-native agency。付费点是 CI gate、私有部署、schema policy、敏感字段规则、migration graph review、PR receipt、审计历史和团队 seat。

## MVP 实验

### 7 天 MVP

只支持 TypeScript + Postgres + Prisma/Drizzle 其中一个入口，不要一上来跨所有 ORM。

输入：

- repo 代码。
- 当前数据库 schema 或 introspection dump。
- migration 文件。
- agent PR diff。
- 简单 policy：敏感表、敏感字段、禁止操作、查询预算。

输出：

- `db-contract.json`。
- PR 评论里的 contract diff。
- 三类结果：`safe` / `needs-human-review` / `blocked`。

第一批检查只做这些：

1. 字段删除和代码引用冲突。
2. migration graph 与 main 分支冲突。
3. 敏感字段读写变化。
4. 新 query 是否缺索引。
5. contractHash 是否和生成类型一致。

### 30 天验证

找 8 个每天使用 coding agent 的 SaaS 团队。每队选择 5 个数据库相关 PR，比较三组数据：

- 人工 review 用时是否下降。
- DB 相关返工是否提前暴露。
- 团队是否愿意把 gate 设成 required check。

不要用“生成了多少 migration”做核心指标。核心指标是：更少事故、更快合并、更少 reviewer 心智负担。

## 商业化路径

1. **开源 CLI + GitHub Action。** 先拿开发者信任，支持本地生成 contract 和 PR receipt。
2. **托管 team policy。** 收团队 seat、repo 数、PR 检查次数、历史审计。
3. **私有部署 / VPC。** 数据库 schema 和 policy 很敏感，大客户会要求内网跑。
4. **Agent platform plugin。** 接入 Claude Code、Codex、Cursor、OpenCode，让 agent 动 DB 前先拉 contract，动完自动生成 receipt。
5. **数据库平台合作。** 和 Neon、Supabase、Prisma、PlanetScale、Railway 这类平台做 branch + contract + migration review 的组合。

## 反例 / 风险

1. **Prisma 自己可能吃掉一部分。** 如果 Prisma Next 的 contract-first 工具链足够强，Prisma 用户未必需要独立层。
2. **跨 ORM 很难。** Rails、Django、Prisma、Drizzle、SQLAlchemy 的迁移语义不同。第一版必须窄。
3. **假阳性会烦死人。** 如果每个 PR 都报一堆无用 warning，团队会关掉 gate。
4. **数据库事故不只来自 schema。** 数据质量、业务约束、异步任务、外部副作用也会炸。contract 只能覆盖一部分风险。
5. **企业安全门槛高。** 真实 schema、表名、字段名本身就是敏感信息。默认本地运行和脱敏输出很重要。
6. **平台集成可能变成重活。** CI、ORM、数据库、agent 工具链都在快速变，维护成本高。

## 可验证指标

- DB 相关 PR 的 review 时间下降幅度。
- contract gate 拦截到的真实问题数量。
- 每 100 次检查的假阳性数量。
- migration graph conflict 在合并前发现的比例。
- agent PR 合并后数据库相关回滚次数是否下降。
- 团队是否把它设成 required CI check。
- contract receipt 被 reviewer 展开阅读和评论的比例。

## 创业判断

这个方向值得跟。数据库是 coding agent 从 demo 进入生产工程的硬边界之一。

但不要做“大而全 AI ORM”。那会撞上 Prisma、Drizzle、Supabase、Neon 和云厂商。更好的切口是：agent database contract gate。它不替代现有 ORM，而是在 agent 改 DB 前后提供机器可读 contract、migration graph review 和 PR receipt。

如果它能让一个数据库相关 agent PR 从“我不敢合”变成“我知道哪里需要人确认”，就有付费理由。
