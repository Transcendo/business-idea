# Agent Database Branching Sandbox

## 一句话判断

AI coding agent 真正进生产工程后，数据库测试瓶颈会从“有没有 staging”变成“每个 agent 任务能不能拿到可写、隔离、可清理的真实数据分支”。

这不是普通 database branching 的旧故事。变化在于 agent 会并行改代码、写 migration、跑 backfill、修数据清洗逻辑。共享 staging 扛不住这种工作方式。

## 赛道 / 产品信号

Ardent 在 HN 以 Launch HN 形式出现，标题很直接：Postgres sandboxes in seconds with zero migration。HN 信号不算小：96 points、48 comments。

Ardent 官网把定位写成“Database branching for coding agents”：给 coding agents 创建任意 Postgres 数据库副本，号称 6 秒内完成，让 agent 在 1:1 的 production postgres copy 上验证代码。官网还强调：clone 在 compute 和 storage 层隔离、只为变更部分付费、scale to 0、适合 migration testing、backfills、data cleaning。

HN 评论区反而更有价值。有人质疑：把生产数据交给新公司不现实；真实数据里可能藏着会触发外部系统副作用的字段；read replica 是否已经够用。创始人回应的关键点是：read replica 不能测试写入；branch hooks 可以在分支返回前跑 SQL，做匿名化和修改。

判断：这里的创业机会不是“再做一个数据库云”。更窄的机会是 agent 任务级数据库沙箱：让每个 AI worker 拿到自己的可写 DB 分支，跑完后留下测试 receipt，而不是污染共享环境。

## 用户痛点是什么

开发团队用 coding agent 后，会更频繁遇到这些坑：

1. **真实数据不可碰。** 生产库最像真实世界，也最不能让 agent 乱试。
2. **共享 staging 很脏。** 多个工程师和 agent 同时写，状态互相污染，失败很难归因。
3. **read replica 不够。** 迁移、回填、数据修复、约束变更都需要写入测试。
4. **本地 fixture 太假。** 单元测试能过，真实数据里的空值、历史脏数据、长尾字段会把 migration 打爆。
5. **准备环境太慢。** 人要导数据、脱敏、建库、跑 seed、清理。agent 本来想提速，结果卡在环境准备。

真正痛点是：agent 能改代码，但没有安全、快速、可复现的数据练兵场。

## AI-native wedge

最小 wedge：

**用户把一个 coding-agent 任务交给系统；系统自动创建一次性 Postgres 分支，按规则清理敏感字段，运行 migration / backfill / 测试，再输出一张可审查的 DB test receipt。**

第一版不要做全数据库平台。只咬住三件事：

- branch：为每个 agent run 创建独立可写数据库分支。
- scrub：按团队规则清理或替换高风险字段，避免 agent 触发外部副作用。
- verify：跑 migration、查询断言、回填校验，输出通过 / 失败 / 数据影响摘要。

AI 压缩的不是“建库”这一个动作。它压缩的是从“我要改一个涉及数据的需求”到“我知道这次变更在真实形态数据上没炸”的整段人工准备和复盘。

## 为什么现在

- Coding agent 正从写小函数走向改模块、改 schema、写 migration。数据库开始成为 agent 工程化的硬瓶颈。
- 多 agent 并行会放大环境隔离需求。一个共享 staging 不可能同时服务十几个 agent run。
- 真实数据问题靠 mock 很难覆盖。AI 写代码越快，越容易把数据层长尾 bug 带进 PR。
- Postgres branching、copy-on-write clone、serverless compute 已经接近可商品化。
- HN 评论里的质疑也说明市场边界清楚：隐私、外部副作用、信任和自托管会决定谁能买。

## 用户为什么来 / 留 / 传播 / 付费

**为什么来：**

用户刚经历过一次 agent 改坏 migration、把 staging 弄脏、或者 PR 里没人敢合并数据层变更。此时他要的不是更聪明的模型，而是安全试错环境。

**为什么留：**

每次 agent run 都能留下数据库验证记录。团队会逐渐形成“涉及 DB 的 agent PR 必须带 branch receipt”的习惯。

**为什么传播：**

可传播的是 PR 里的验证卡片：

```md
DB branch: pr-482-agent-run-17
Migration: passed
Backfill sample: 50k rows checked
Risk fields: scrubbed by rule set v3
Data diff: 2 tables changed, no unexpected writes
Cleanup: branch destroyed after CI
```

这比“我们支持数据库分支”更像工程团队会转发的东西。

**谁付费：**

AI-heavy SaaS 团队、金融 / 医疗 / 企业软件团队、AI-native agency、agent coding 平台、内部平台团队。付费点是私有部署、VPC、审计记录、团队规则、CI 集成、数据清理策略和并发分支额度。

## MVP 实验

### 7 天 MVP

只支持 Postgres + GitHub Actions + 一个 coding agent：

```bash
agent-db-branch create --from prod-snapshot --ttl 2h
agent-db-branch scrub --rules scrub.yml
agent-db-branch verify --cmd "pnpm test:migrations"
agent-db-branch receipt --out db-receipt.md
```

输入：数据库连接、脱敏规则、migration 命令、测试命令。

输出：

- 一次性 DB 分支。
- schema diff 和关键表写入摘要。
- 失败 SQL / migration step 摘要。
- PR 可读 receipt。

先不碰所有数据库。先做 Postgres，先服务“agent 改 schema / migration / backfill”的窄任务。

### 30 天验证

- 找 8-10 个每天用 Claude Code / Codex / Cursor 的工程团队。
- 每队挑 3 个真实 DB 相关 PR。
- 对比人工准备 staging / fixture 的时间和自动分支时间。
- 记录 agent PR 因数据问题返工的次数是否下降。
- 看团队是否愿意把 DB receipt 设成合并前检查项。

## 可验证指标

- 创建可写数据库分支的 P50 / P95 时间。
- 每个 agent run 的环境准备时间下降幅度。
- migration / backfill 问题在 PR 前被拦截的次数。
- 生成 receipt 后人工仍需补查的比例。
- scrub 规则误伤和漏放的比例。
- 分支销毁成功率和残留成本。
- 团队是否把它接入 CI，而不是只试一次 demo。

## 商业化路径

1. **开源 CLI / GitHub Action。** 先让小团队在非核心库上试。
2. **托管 Postgres branch service。** 收并发分支、运行时长、存储变更量。
3. **企业私有部署。** VPC、审计、团队规则、数据清理策略。
4. **Agent 平台集成。** 给 Claude Code、Codex、Cursor、OpenCode 工作流暴露“拿 DB 分支并验证”的工具。
5. **垂直包。** 金融账务、医疗记录、B2B SaaS 多租户数据，各自有不同的 scrub 和断言模板。

## 反例 / 风险

1. **信任门槛极高。** 很多公司不会把真实生产数据交给早期创业公司。自托管或 VPC 可能不是高级功能，而是入场券。
2. **外部副作用难消。** 数据库里可能有 webhook 地址、第三方系统标识、客户集成配置。只隔离数据库不等于隔离世界。
3. **平台会下场。** Neon、Supabase、AWS、GCP、Vercel、agent coding 平台都有能力把基础能力做进自家产品。
4. **成本模型容易爆。** 多 agent 并发、TB 级数据库、长时间分支会把存储和计算账单打穿。
5. **测试不等于正确。** 如果只跑 migration 成功，不检查业务语义，receipt 会变成假安全感。
6. **非 Postgres 扩展慢。** MySQL、MongoDB、Snowflake、BigQuery、multi-tenant 数据库形态差异很大。

## 创业判断

这个方向值得跟，因为它抓住了 AI coding 从“会写代码”到“敢改生产系统”的关键断点。

最好的早期产品不是大数据库平台，而是 coding-agent DB safety kit：每个 agent run 一个隔离 DB 分支，自动清理风险字段，跑真实迁移测试，输出 PR receipt。

如果它能把一个 DB 相关 PR 的环境准备从半天压到 5 分钟，并且真的拦住一次危险 migration，工程团队会付钱。
