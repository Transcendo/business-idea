# Durable Agent Workflow Runtime

## 一句话判断

多步骤 AI agent 开始进生产后，机会不是再做一个更花的流程画布，而是把 agent 任务封成可暂停、可恢复、可观测、可审计的 durable workflow runtime。

这个方向卖的不是“我也能编排 agent”。真正值钱的是：**长任务跑到一半断了、等人工审批、调用外部系统、换模型、重试失败时，团队仍然知道状态在哪里，下一步该怎么恢复。**

## 赛道 / 产品信号

这轮信号很清楚：agent 框架在变多，但生产团队开始缺统一的运行层。

- Vercel 的 Workflow SDK README 直接写明：给 async JavaScript 增加 durability、reliability、observability，面向 apps 和 AI agents，支持 suspend、resume、maintain state。
- OpenAI Agents SDK README 把 multi-agent workflows、handoffs、guardrails、human-in-the-loop、sessions、tracing 都列为核心概念。它说明 agent 不再只是一次聊天，而是一组可交接、可追踪的任务。
- Google ADK README 把自己定义为 build、evaluate、deploy sophisticated AI agents 的 code-first framework，并强调 deployment-agnostic、model-agnostic、compatible with other frameworks。
- Activepieces 的 GitHub 描述已经把 AI Agents、MCPs、AI Workflow Automation 放在一起，说明传统自动化工具也在向 agent workflow 迁移。
- HN 上有人提交 runtime-agnostic AI agent workflow spec，项目 README 明确写“spec is the contract”，并支持编译到 LangGraph、CrewAI、Mastra、A2A。热度不高，但暴露了一个真实痛点：团队不想被单一 agent 框架锁死。

这些不是一个产品的孤立信号，而是一类基础设施正在成形：agent 要进真实业务，就必须有 durable workflow runtime。

## 用户痛点是什么

今天很多 agent demo 的假设太乐观：一次 prompt，模型想清楚，工具调用顺利，最后返回答案。

生产里的任务不是这样。

真实 agent workflow 会遇到：

- 外部 API 限流、超时、schema 改动。
- 人工审批卡住，比如付款、发邮件、改配置、合并 PR。
- 子 agent 做完一半，主 agent 丢了上下文。
- 浏览器、数据库、文件、MCP 工具状态和模型消息不一致。
- 重试后重复执行危险动作，比如重复下单、重复发通知、重复写库。
- 业务方只看到“失败了”，看不到失败节点、输入、输出、成本和恢复建议。

普通 workflow engine 不懂 LLM 的不确定性。普通 agent framework 又往往不擅长 durable execution。缺口就在中间。

## AI-native wedge

最小 wedge：

> 用户把一个多步骤 agent 任务定义成 run spec；系统负责状态机、暂停恢复、人工审批、工具幂等、trace、成本、失败回放和最终 receipt。

第一版别做“大一统 agent 平台”。只做一个硬窄场景：

1. 输入一个任务 spec：目标、步骤、可用工具、模型、预算、审批点、验收条件。
2. 每个节点记录输入、输出、tool call、模型版本、成本、状态和恢复策略。
3. 支持 `pause`、`resume`、`retry from node`、`human approve`、`cancel`。
4. 对外输出 run receipt：跑了什么、卡在哪里、是否安全完成、下一步谁负责。

AI 负责把模糊任务拆成行动和判断。runtime 负责让行动可控、可恢复、可复查。

## AI 是否真的压缩任务

压缩的是“人类协调多系统”的时间。

例如一个销售线索清洗任务，原来要人查 CRM、补公司信息、判断优先级、写跟进话术、等负责人批准、同步回系统。agent 可以把查找、归纳、排序、起草压成一条任务链。

但如果没有 durable runtime，失败一次就会变成脏聊天记录。工程师或运营要重新读上下文、猜哪些动作已经执行、手动补偿。那就不叫自动化，叫把事故藏进黑盒。

所以这个方向的判断标准不是“agent 多聪明”，而是“失败后人能不能在 2 分钟内恢复现场”。

## 为什么现在

几个变化同时发生：

- Agent 框架爆发：OpenAI Agents SDK、Google ADK、LangGraph、Mastra、CrewAI 等都在争夺开发者入口。
- MCP 和 tool calling 让 agent 能接越来越多真实系统，风险也跟着上来。
- 企业开始从 demo 走向内部流程：客服、销售、代码维护、数据分析、运营后台都可能变成长任务 agent。
- Serverless / workflow / queue / trace 基础件成熟，durable execution 有现成工程土壤。
- 团队不想把 workflow spec 锁在某个模型或某个框架里，runtime-agnostic spec 开始变得有意义。

## 用户为什么来 / 留 / 传播 / 付费

**为什么来：** 团队已经试过 agent，但一放进真实流程就卡在重试、审批、trace、幂等和恢复。这个痛点不性感，但很快烧到生产。

**为什么留：** 每个 run 都沉淀状态、失败节点、成本、人工决策和最终 receipt。历史越多，团队越能知道哪些流程能自动跑，哪些节点必须人工守门。

**为什么传播：** 最容易被转发的是 run card：一个 agent workflow 跑了 18 分钟，完成 7 个节点，在付款节点暂停，审批后恢复，最终写回 CRM。业务和工程都看得懂。

**为什么付费：** 免费层可以做本地 spec runner。团队付费点在托管 runner、私有部署、审计日志、审批策略、SaaS 集成、成本控制、并发任务、合规保留、跨框架迁移。

## MVP 实验

MVP 可以从一个垂直流程切入，不要一上来做通用画布。

推荐实验：**AI 销售/运营后台任务 runtime**。

1. 只支持 3 类工具：HTTP API、数据库只读查询、人工审批 webhook。
2. 内置 5 个节点：research、classify、draft、approve、writeback。
3. 每个节点都要求 schema 输出和幂等 key。
4. 失败时允许从指定节点恢复，不允许全链路盲重跑。
5. 输出一张 run card，业务方能看懂，工程方能复查。
6. 找 5 个团队跑真实任务：线索清洗、客户摘要、工单分流、周报生成、内容发布前检查。

验证点不是“能不能跑通一次”，而是“连续 100 次任务后，失败率、恢复时间、重复执行事故和人工审批负担是否下降”。

## 商业化路径

可能客户：

- AI-heavy SaaS 团队：已经有 agent 功能，但缺运行层。
- 内部工具团队：想把 agent 接进 CRM、工单、数据后台和审批流。
- 自动化平台：Zapier / n8n / Activepieces 类产品的 AI 化压力很大，需要 agent runtime，而不只是节点编辑器。
- 合规敏感团队：金融、医疗、企业服务不敢让 agent 黑盒执行。

定价可以按 runner 并发、workflow run 数、审计保留期、私有部署、集成数量、审批 seat 走。真正的大单来自“我们要让 agent 执行业务动作，但必须可审计”。

## 反例 / 风险

1. **平台吸收风险很高。** OpenAI、Google、Vercel、LangChain、Zapier、n8n 都可能把 durable runtime 做成平台能力。创业公司不能只卖通用编排。
2. **太早做画布会死。** 画布用户多，付费意愿未必高。先抓有真实恢复成本的流程。
3. **幂等和补偿很难。** Agent 重试不是普通函数重试。外部系统可能已经发过邮件、写过库、扣过款。
4. **开发者体验容易变重。** 如果 spec 太复杂，团队会退回简单脚本和 LangGraph。
5. **安全责任会被推给 runtime。** 一旦 agent 执行危险动作，客户会问为什么 runtime 没有挡住。

## 可验证指标

- 100 次真实 workflow run 的完成率。
- 失败后中位恢复时间是否低于 2 分钟。
- 重复执行外部动作的事故数是否接近 0。
- 人工审批节点是否能减少无效打扰。
- 每次 run 的 trace 是否足够让工程师复盘。
- 非工程用户是否能读懂 run card。
- 团队是否愿意把第二个业务流程迁进来。

## 后续跟踪点

- OpenAI / Google / Vercel 是否把 durable execution 做成默认 agent runtime。
- LangGraph、Mastra、CrewAI、ADK 之间是否出现可迁移 spec。
- 自动化平台是否把 MCP 和 agent 节点做成可审计的长任务。
- 企业用户是否愿意为 run receipt、审批、恢复、审计单独付费。
