# Headless Coding Agent Runtime

## 一句话判断

AI coding 的下一层机会不是再做一个 IDE 插件，而是把同一个 coding agent 封成 CLI、SDK、CI/CD、任务队列和产品内嵌自动化都能调用的 headless runtime。

这个方向卖的不是“更聪明的补全”，而是：**让团队把 coding agent 放进真实工程流程，跑完、留证据、能恢复、能审计。**

## 赛道 / 产品信号

这轮信号很集中：

- Cline 的 GitHub README 已经把自己从 IDE extension 扩成 “open source coding agent in your IDE and terminal”，并列展示 CLI、Kanban、VS Code、JetBrains 等入口；GitHub API 显示仓库已有 61k+ stars、6k+ forks，仍在近期发布。
- Cline CLI README 明确写了两种使用方式：interactive chat 和 fully headless for CI/CD and scripting。这把 coding agent 从编辑器按钮推到了脚本和流水线里。
- Cline SDK README 把 `@cline/sdk` 定位成 TypeScript framework：可以编辑文件、跑 shell、浏览网页、调用 API、接自定义工具，并嵌入自己的应用。
- npm registry 已经有公开的 [`@cline/sdk`](https://www.npmjs.com/package/@cline/sdk) 包。它不是概念页，而是可安装的开发者入口。
- GitHub issue 里已经出现 headless 使用的真实摩擦：比如 CLI 在工具调用出错后提前停止、headless server 上 auth 需要浏览器导致卡死。

这说明 coding agent 正在从“人坐在 IDE 前让它改代码”走向“系统在后台调度它完成工程任务”。

## 用户痛点是什么

今天的 AI coding 工具强在单次对话，弱在工程化运行。

真实团队想要的是这些动作：

- 在 CI 失败后自动开一个 agent run，尝试修复并提交 PR。
- 每晚跑依赖升级、lint 修复、文档同步、低风险重构。
- SaaS 产品内嵌一个 agent，让客户在自己的 repo 上生成插件、报表、集成代码。
- 多个 agent 并行处理 backlog，每个任务有隔离工作区、预算、日志、人工审批和回滚。
- 失败后不是丢一段聊天记录，而是留下可复跑的 run receipt。

IDE 插件解决“我现在要改这段代码”。headless runtime 解决“系统要把一批工程任务可靠地交给 agent”。这是两个市场。

## AI-native wedge

最小 wedge：

> 用户给一个 GitHub repo、任务描述、预算、允许工具和验收命令；系统启动一个隔离 coding-agent run，自动拉分支、改代码、跑测试、生成 diff、写 run receipt，并在失败时保留可恢复现场。

这个 wedge 不应该一上来做完整工程平台。先把三件事做硬：

1. **任务封装**：把 prompt、repo、branch、环境、secrets policy、允许命令、验收标准固化成一个 run spec。
2. **执行可控**：headless agent 可以跑，但所有高危动作有预算、路径边界、超时、人工审批和日志。
3. **结果可审**：输出 PR / patch / failure receipt，而不是一段聊天。

SDK 的机会在这里：让别的产品不用自己造 agent core，就能把 coding agent 嵌进自己的工作流。

## AI 是否真的压缩任务

压缩得很明显，但边界也很硬。

AI 真正压缩的是这些重复工程劳动：小版本升级、测试修复、样板代码、迁移脚本、issue 初步修复、文档和代码同步、静态检查后的机械修改。它把“人读错误、定位文件、改几处、跑命令、整理 PR”的链路压成一次 run。

它压不掉的是产品判断、架构取舍、危险迁移、线上事故责任和复杂多人协作。headless runtime 的价值不是让 AI 自己当工程师，而是让低风险工程任务变成可调度、可限制、可审计的后台作业。

## 为什么现在

几个变化叠在一起：

- Coding agent 已经足够能改真实 repo，不再只是 autocomplete。
- 团队开始同时使用 Cursor、Claude Code、Cline、Codex、JetBrains agent 等工具，单一 IDE 入口不够。
- CI/CD、GitHub Actions、Linear/Jira、Slack 这些系统天然需要后台执行，不适合人工盯着聊天窗口。
- MCP、tool calling、sandbox、worktree、run log、test command 这些基础件开始成熟。
- 开源 coding agent 开始提供 CLI / SDK，说明“可嵌入 agent runtime”正在从内部能力变成开发者商品。

## 用户为什么来 / 留 / 传播 / 付费

**为什么来：** 团队已经在用 coding agent，但很多任务没法靠人守着 IDE。CI 失败、批量 issue、夜间维护、客户 repo 自动化，都需要后台跑。

**为什么留：** 每个 run 都留下任务定义、diff、测试结果、失败原因、审批记录和成本。历史越多，团队越知道哪些任务能交给 agent，哪些必须交给人。

**为什么传播：** 最容易传播的不是产品介绍，而是一张 “agent run card”：输入任务、改了哪些文件、跑了哪些命令、哪里失败、PR 链接。工程团队会把它丢进 GitHub、Slack、Linear。

**为什么付费：** 个人开发者可能愿意为 CLI 付少量费用。真正的钱在团队版：并发 run、私有 runner、secrets 隔离、GitHub/Linear/Jira 集成、审批策略、成本控制、审计日志、企业模型网关。

## MVP 实验

MVP 可以很窄：

1. 只支持 GitHub repo + Docker/sandbox runner。
2. 输入一个 issue URL 或纯文本任务。
3. 用户配置允许路径、禁止路径、预算、超时和测试命令。
4. 后台启动一个 coding-agent run，自动创建分支。
5. 成功时开 PR；失败时输出 failure receipt。
6. 对 10 个团队测试 3 类任务：CI 修复、依赖升级、小 bug issue。
7. 对比人工处理和 headless agent run 的耗时、成功率、回滚率、审查负担。

先别做“多 agent 大脑”。先证明单个 headless run 能稳定交付低风险工程任务。

## 商业化路径

最自然的客户：

- AI-heavy startup：工程速度快，愿意让 agent 处理维护任务。
- Devtool / infra 公司：要把 coding agent 嵌进自己的产品。
- 外包 / agency：大量重复 repo 任务，愿意用后台 agent 降低返工。
- 企业平台团队：想统一管理不同 coding agent 的权限、成本和审计。

定价可以按 runner 并发、run 数、seat、私有部署、集成数量和审计保留期走。SDK 版可以走 usage-based 或商业 license。

## 反例 / 风险

1. **大 IDE 和代码托管平台会直接做。** GitHub、Cursor、JetBrains、Cline、Anthropic、OpenAI 都可能把 headless agent 变成原生功能。创业公司必须切到跨工具、跨平台、企业治理，不能只包一层 CLI。
2. **失败恢复比 demo 难。** Agent 卡住、命令失败、auth 失败、网络不通、测试挂起，都会让后台运行变成脏活。
3. **安全边界很容易出事。** Headless agent 有 shell、文件、git、网络、secret 权限。默认放开就是事故入口。
4. **审查成本可能没降。** 如果 agent 产生大 diff、测试不稳、解释不清，工程师会花更多时间 review。
5. **模型成本不稳定。** 低价值任务如果烧太多 token，很快亏钱。

## 可验证指标

- 低风险任务的首轮成功率是否超过 60%。
- 从任务创建到 PR 的中位时间是否小于人工处理的一半。
- 每个成功 PR 的 token / runner 成本是否可控。
- 工程师 review agent PR 的时间是否低于人工写 PR。
- 失败 run 是否能在 2 分钟内让人判断下一步。
- 高危命令、越界文件修改、secret 触达是否被拦住。
- 团队是否愿意把第二批任务继续交给后台 agent，而不是只试一次。

## 后续跟踪点

- Cline CLI / SDK 是否继续强化 headless、CI/CD、plugin、tool approval 和 run receipt。
- GitHub Copilot、Cursor、Claude Code、Codex 是否推出稳定的后台任务 API。
- 企业是否真的愿意让 coding agent 在 CI/CD 里自动开 PR。
- 开源社区是否出现跨 agent 的 run spec、receipt、sandbox 标准。
- Headless coding agent 的失败日志是否能沉淀成 eval / regression harness。
