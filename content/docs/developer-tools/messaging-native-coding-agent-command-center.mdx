# Messaging-Native Coding Agent Command Center

## 一句话判断

AI coding agent 正在从“坐在 IDE 里补全代码”变成“在终端里跑几十分钟的执行者”。问题也跟着变了：用户不一定坐在电脑前，但 agent 会随时卡在确认、测试失败、权限、分支冲突、外部命令和下一步选择上。

机会不是再造一个 coding agent。机会是做 messaging-native coding agent command center：把 Claude Code、Codex、OpenCode 这类 agent 的开始、直播、批准、暂停、恢复、总结和交接，压进 Slack、Discord、Telegram、微信、飞书这些团队和个人已经在看的消息线程。

## 赛道 / 产品信号

Vibe Remote 是很直白的信号。它的 GitHub 描述是：用 Slack、Discord、Telegram、WeChat、Lark 指挥 Claude Code、OpenCode 或 Codex，并实时 stream。README 里更狠：聊天 App 变成 terminal，用户可以从手机继续当前项目里的 agent session。

AgentSys 给出另一个侧面：模型会写代码之后，难点变成 task selection、branch management、code review、artifact cleanup、CI、PR comments、deployment。也就是说，agent 的价值越来越在“执行链路”里，不只在模型输出里。

Reddit 的 r/ChatGPTCoding 和 r/OpenAI 也暴露了两个真实摩擦：用户关心 AI coding 工具在哪一步会掉链子，也关心 Codex / ChatGPT 的使用限制和 token 配额。长任务 agent 如果没有清楚的状态、预算和人为批准入口，很容易从“省时间”变成“烧时间”。

判断：这不是一个纯 UI 小玩具。它是 agent ops 的入口层。终端本身不适合做多人协作、移动审批和异步交接；消息线程适合。

## 用户痛点是什么

1. **Agent 长任务需要人看着。** 它会跑测试、改文件、执行命令、等权限、问问题。人一离开电脑，进度就断。
2. **移动场景缺入口。** 用户在路上、会议中、吃饭时，仍然可能需要批准一个命令、回答一个 scope 问题、让 agent 停下。
3. **多个 agent session 难管理。** 一个 repo 一个终端还好，多 repo、多任务、多工具时，谁在跑、谁卡住、谁需要批准会变成黑箱。
4. **团队协作不在终端里。** 工程讨论、PR 决策、风险确认通常发生在 Slack/Discord/飞书，而不是本地 shell。
5. **风险动作缺短凭证。** Agent 要跑 migration、push、删文件、调用外部 API 时，用户需要的是一张可审查 approval card，不是一大坨 terminal log。

痛点不是“开发者懒得打开电脑”。痛点是 coding agent 把软件开发变成异步长任务，但现有控制面还停留在本地同步终端。

## AI-native wedge

最小 wedge：

用户在一个聊天线程里发起 coding agent 任务；系统在本机或远端启动真实 agent；所有关键状态以消息流和 approval card 形式返回。

这张 command card 要包含：

- 当前 repo、branch、agent、任务目标。
- agent 正在做什么，卡在哪一步。
- 最近 diff 摘要和测试结果。
- 下一步风险等级。
- 待批准动作，例如运行命令、访问网络、改数据库、push、开 PR。
- 可选按钮：approve、pause、resume、summarize、handoff、stop。

AI 压缩的任务不是“把聊天当 IDE”。它压缩的是从“人必须守在终端旁边”到“人只在关键判断点介入”的整段协作和监督成本。

## 为什么现在热

- Claude Code、Codex、OpenCode、Cursor agent 让 coding 任务变成长会话。长会话自然需要远程状态和中途批准。
- 团队已经把 Slack、Discord、飞书当作工作流入口。把 agent 操作带进消息线程，比让所有人学习新控制台更顺。
- Vibe Remote 这类开源项目开始把 Slack、Discord、Telegram、微信、飞书直接接到真实 coding agent 上，说明 builder 已经在抓这个痛点。
- AgentSys、skillfile、MCP 工具链等项目让 agent session、技能、插件和工具越来越多。入口分散之后，统一 command center 的价值会上升。
- 移动审批和异步交接是现成付费点。企业不一定为“更炫的 agent UI”付钱，但会为“谁批准了哪个 agent 动作，出了事能回看”付钱。

## 用户为什么来 / 留 / 传播 / 付费

### 为什么来

用户刚遇到过这种场景：agent 跑到一半问问题，自己不在电脑前；或者一个终端挂了一下午，回来发现它早就卡住。此时他们要的不是更强模型，而是随时能接管和批准。

### 为什么留

一旦团队把 coding agent 的 blocker、approval、PR summary 放进消息线程，它会进入日常节奏。工程师不需要反复打开不同终端看状态，团队 lead 也能看到哪些 agent 正在烧时间。

### 为什么传播

传播单元很直观：

```md
Task: fix login redirect bug
Agent: Claude Code
Status: tests failing on auth.spec.ts
Risk: medium
Diff: 4 files changed
Action needed: approve running migration? no
Buttons: summarize / continue / stop / open PR
```

“我在微信/Slack 里让 agent 修好了一个 repo”比“我装了一个新的 IDE 插件”更容易被截图和转发。

### 谁付费

AI-heavy 开发团队、AI coding agency、远程团队、内部平台组、使用多 agent 的创业团队、需要审计的企业工程组织。付费点是团队 seat、私有部署、聊天平台集成、审批策略、敏感命令拦截、session 历史、PR/CI 接入、多 agent 队列和审计导出。

## MVP 实验

### 7 天 MVP

只支持一个聊天入口、一个 agent、一个 repo。不要一上来做全平台。

推荐窄切口：Discord 或 Slack + Claude Code / Codex + GitHub repo。

输入：

- 聊天消息里的任务描述。
- repo path / branch。
- 可执行 agent 命令。
- 简单 policy：哪些命令必须确认，哪些路径禁止改，哪些动作只能 summary。

输出：

- 实时状态消息。
- 每 5-10 分钟的短 summary。
- 风险动作 approval card。
- 停止 / 继续 / 总结 / 开 PR 按钮。
- 任务结束 receipt：改了什么、测了什么、哪里失败、下一步是什么。

第一版只做这些检查：

1. shell 命令批准。
2. git diff 摘要。
3. 测试结果摘要。
4. 长时间无输出提醒。
5. agent 卡住时主动请求人类决定。

### 30 天验证

找 10 个每天用 coding agent 的开发者或小团队。每人跑 10 个真实任务，比较三组数据：

- agent 卡住后到人类响应的时间是否下降。
- 任务完成率是否提高。
- 用户是否愿意在手机或团队聊天里批准下一步。
- 是否愿意把它接入工作 Slack/飞书，而不只是个人玩具。
- 是否愿意为 team audit / approval policy 付费。

核心指标不是“发了多少条消息”。核心指标是：更少 dead session、更快 unblock、更清楚的风险批准、更高任务完成率。

## 商业化路径

1. **开源本地 bridge。** 先让开发者信任它不偷代码、不托管 repo，只把本地 agent session 接到聊天入口。
2. **Team command center。** 多 repo、多 agent、多成员、权限、队列、session handoff、PR receipt。
3. **Approval policy。** 对 push、migration、删除文件、访问网络、调用生产 API 等动作做规则和审计。
4. **企业私有部署。** 消息平台、代码、agent logs 都很敏感，大客户会要求自托管或 VPC。
5. **Agent platform plugin。** 给 Claude Code、Codex、OpenCode、Cursor、OpenClaw 等工具提供通用 messaging adapter。

## 反例 / 风险

1. **Agent 厂商可能直接做。** Claude、OpenAI、Cursor 都可能把移动端和 Slack/飞书集成做进官方产品。
2. **聊天噪音会反噬。** 如果每个 token 都 stream 到频道，团队会马上静音。必须做摘要和风险分级。
3. **安全边界很难。** 聊天入口一旦能批准 shell/git/API 动作，就必须处理身份、权限、审计和误触。
4. **个人用户可能只觉得新奇。** 付费产品必须证明 completion rate 和 unblock time 改善，而不是手机远程终端玩具。
5. **跨平台维护成本高。** Slack、Discord、Telegram、微信、飞书的权限、消息格式和审核规则都不同。
6. **代码隐私敏感。** 默认不应把完整 diff、secret、长日志发到第三方聊天平台。需要脱敏和最小摘要。

## 可验证指标

- agent session 的卡住时长是否下降。
- 人类从收到 blocker 到批准/拒绝的中位时间。
- 每 100 个任务的完成率变化。
- 每个任务的人工查看终端次数是否下降。
- 风险 action card 的 approve / reject / timeout 比例。
- 用户是否把它接入团队频道，而不是只私聊机器人。
- 任务结束 receipt 是否被转发到 PR 或 issue。
- 团队是否愿意为审批策略和审计历史付费。

## 创业判断

这个方向值得跟，但不能做成“聊天版远程终端”。那太浅，也容易被官方吃掉。

更好的切口是：messaging-native agent command center。它把长任务 agent 的状态、风险、批准和交接变成团队已经理解的消息工作流。真正卖点不是多接几个聊天 App，而是减少 dead session、降低监督成本、留下谁批准了什么的证据。

如果它能让团队放心地并行跑多个 coding agent，并且不用守在终端旁边，那就有付费理由。
