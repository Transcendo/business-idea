# DrSwarm

## 一句话判断

DrSwarm 值得跟踪的点很直接：它没有讲“通用医疗 AI”，而是盯住 ambulatory clinics 和 health systems 里那些高频、重复、但很贵的运营工作。这个切口更像可卖的 workflow software，而不是概念产品。

## 这家公司在做什么

DrSwarm 的官网和 LinkedIn 都把自己定义成面向诊所和小型 health system 的 AI operations team。它的重点不是替医生写病历，而是接手医疗机构日常后台工作。

它公开列出的场景包括：

- scheduling
- patient communications
- insurance and billing follow-ups
- referrals
- inbox triage
- administrative task routing

它强调这些 agent 是工作在现有 EHR 和 RCM 系统之上的，而不是要求医院重建系统。

## 为什么值得关注

1. **切口够窄，也够真。** 这些工作不是“未来可能需要”，而是医疗机构每天都在烧钱的现实负担。

2. **买单方明确。** 诊所、运营团队、health system 的行政部门都能直接感受到节省人力和减少延迟。

3. **更像工作流基础设施。** 不是卖一个聊天界面，而是把杂乱的运营任务变成可监控、可交接的执行层。

4. **适合从单点扩张。** scheduling、billing follow-up、referral 这类任务之间有共性，容易沿着操作链继续扩。

## 风险与观察点

1. **集成复杂。** 医疗后台系统碎、老、例外多，agent 很容易在边角 case 上出问题。

2. **可靠性门槛高。** 一旦碰到保险、账单、患者沟通，错一次的代价都不低。

3. **采购不会快。** 即便 ROI 清楚，医疗机构对权限、审计、HIPAA 的审查依然慢。

4. **“AI ops team” 叙事容易泛化。** 关键要看它到底先把哪一个流程做到稳定，而不是只看口号。

## 我们的判断

DrSwarm 是一个值得继续盯的医疗 AI 方向：从 clinic ops 切入，把医院和诊所最烦的后台工作做成可执行 agent layer。它更像长期能落地的 workflow 产品，而不是短期热度。

后续重点看三件事：
- 是否能在真实诊所里稳定跑通；
- 是否有清晰的付费客户和可复用流程；
- 是否从运营单点扩到更广的 healthcare workflow。
