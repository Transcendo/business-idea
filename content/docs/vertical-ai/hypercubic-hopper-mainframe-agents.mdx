# Hypercubic Hopper Mainframe Agents

## 一句话判断

Hopper 值得看，不是因为“COBOL 也能用 AI”这个噱头，而是因为它切进了一个大厂很难轻松替换、年轻工程师又越来越不熟的系统层：mainframe operations。

如果 AI agent 只是在浏览器里点按钮，这个方向没什么稀奇。Hopper 更像是把 TN3270 终端、datasets、JES jobs、COBOL/JCL/CICS 操作和审批卡合到一个 agentic development environment 里。它压缩的是老系统里的查找、提交、排错、验证和交接成本。

这个市场不会像 consumer AI 那样炸裂传播，但它有一个创业者该认真看的特点：痛点很旧，预算很真，替换成本很高，AI 的任务压缩又足够具体。

## 赛道 / 产品信号

Hopper 属于垂直 AI + enterprise developer tools + agent runtime。

本轮信号：

- 2026-05-12 的 HN Show HN 帖 `Agentic interface for mainframes and COBOL` 拿到约 50+ points、30 comments。讨论点集中在 COBOL/mainframe 人才断层、生产系统安全、AI 是否能可靠操作老环境。
- 官方页面把 Hopper 定义为 `the first agentic development environment for the mainframe`，支持导航 TN3270、检查 datasets、写 JCL、debug jobs、查询 VSAM、在 z/OS 内操作。
- 官方 docs 写得很具体：一个 mainframe session 暴露为四个面板：TN3270 terminal、datasets browser、jobs browser、AI agent。四者共享状态。
- 工具层不是泛泛“读写文件”。官方列出的能力包括 datasets、jobs、terminal、CICS、COBOL、data taps。mutating action 必须逐次审批，隐藏字段先在本地被 placeholder 替换，凭证不进模型上下文。
- 定价信号也清楚：Hobby 免费，Enterprise 才给 SAML SSO、MCP Server Access、Admin and Model Controls、Org-wide Privacy Controls、No Model Training、on-prem / VPC、SOC 2 和 Pen Test Reports。

这不是普通 AI coding 工具的换皮。它的关键是：把一个老、贵、难招人的系统环境变成 agent 可操作但人类可控的任务界面。

## 用户痛点是什么

Mainframe 不是没人用，而是仍然太多人离不开。

真实痛点不是“用户不会写代码”，而是：

1. **操作链条古老。** TN3270 是 block-mode terminal，屏幕状态、PF keys、AID keys、字段保护、EBCDIC、JES spool、PDS member 这些概念对新工程师不友好。
2. **排错成本很高。** 一个 failed job 可能要翻 JESMSGLG、JESYSMSG、SYSUDUMP，找 abend code、failing step、source line。老手能做，新人会卡半天。
3. **知识在少数人脑子里。** COBOL、JCL、CICS、VSAM、copybook、production runbook 往往靠资深工程师传。人走了，系统还在。
4. **改动风险大。** 这不是改一个前端按钮。错的 JCL class、CICS resource install、bulk manifest deploy 都可能影响生产。
5. **现代 DevTool 很难覆盖。** VS Code 插件或通用 agent 很难直接理解 TN3270 屏幕状态、mainframe filesystem 和 job queue。

用户真正想要的是：让新人能完成老系统任务，让老手少做重复 triage，同时不要把生产权限交给一个乱跑的模型。

## AI-native wedge

最小 wedge：

**用户用自然语言描述一个 mainframe 任务；系统读取当前 terminal / dataset / job 状态，自动完成只读排查，遇到写入、提交 job、发送 terminal key、CICS install 等变更动作时生成审批卡；执行后再验证结果。**

例子：

```txt
任务：为什么 JOB01945 失败？
agent：读取 JES spool -> 分类 abend -> 找到 failing step -> 定位 COBOL source line -> 给出修复建议
人类：批准改 PDS member / 提交 JCL
agent：提交 job -> 等待 return code -> 汇总验证结果
```

AI 压缩的不是“写 COBOL”本身，而是这条脏链路：找对象、读屏幕、读 spool、解释错误、提出下一步、执行前等人批、执行后验结果。

## 为什么现在

- AI coding agent 已经证明了“让模型读代码、改代码、跑命令”这条路可行。企业开始问：更老、更贵、更缺人的系统能不能也被 agent 接管一部分？
- Mainframe 人才老化是真问题。越靠 COBOL/JCL/VSAM/CICS 的系统，越依赖经验传承。AI 不能替代主责工程师，但能让 junior 少死在入口。
- MCP、tool calling、agent approval card 这些基础设施成熟后，agent 能被放进受控动作空间，而不是一个纯聊天机器人。
- 监管和安全要求反而让本地桌面、keychain、逐动作审批、on-prem / VPC 这类设计更有价值。Hopper 没有假装企业会把 mainframe 凭证随便塞进云端模型。
- 旧系统现代化周期太长。很多企业不会马上替换 mainframe，但愿意买“降低维护和排错成本”的工具。

## 用户为什么来 / 留 / 传播 / 付费

**为什么来：**

第一次使用动机很具体：一个 failed batch job、一个看不懂的 TN3270 screen、一个需要改 JCL/COBOL/CICS 的任务，用户不想再从老 runbook 和口口相传里找答案。

**为什么留：**

如果 Hopper 能稳定把“查 spool -> 定位失败 -> 改 member -> submit job -> 验证 return code”这类流程从几小时压到几十分钟，它会成为 mainframe 团队的日常工作台。留存来自重复任务，不来自新鲜感。

**为什么传播：**

传播单位不是炫酷截图，而是事故复盘卡：

```txt
JOB01945 failed: S0C7 in step CBACT01C
agent found field decode mismatch via copybook
human approved PDS patch
rerun RC=0
```

这种卡能在工程团队、咨询交付团队、mainframe modernization 圈子里传播。它不是大众病毒传播，是垂直职业传播。

**谁付费：**

银行、保险、航空、政府承包商、mainframe consulting / modernization 公司。付费理由是 SSO、权限控制、审计、隐私、不训练、私有部署、团队管理、SOC 2 / pen test 报告，以及把资深 mainframe 工程师的时间从重复 triage 里解放出来。

## MVP 实验

### 7 天 MVP

不要一开始做完整 IDE。先做只读排障 assistant：

- 输入：一个 job id、一个 dataset member、一个 TN3270 screen snapshot。
- 输出：失败原因、相关 spool 段落、可能的 source line、下一步操作建议。
- 限制：不做写入，不提交 job，只产出 evidence card。

这一步验证 AI 是否真的能理解 mainframe artifacts，而不是只会讲 COBOL 常识。

### 30 天验证

找 5 个 mainframe 团队或 consulting 小组，拿脱敏 training system / sandbox 做 A/B：

- 任务 1：诊断 failed batch job。
- 任务 2：解释一个 VSAM record / copybook mismatch。
- 任务 3：修改一个 PDS member 后提交 JCL。
- 任务 4：新人根据 agent 指引完成一次 CICS transaction 排查。

核心不是 demo 成功，而是测：老手是否愿意让 junior 用，junior 是否少问人，审批卡是否足够让老手放心。

## 可验证指标

- failed job 从报错到定位 root cause 的中位时间。
- junior 完成标准 mainframe task 的成功率。
- 每个任务需要资深工程师介入的次数。
- agent 建议被批准 / 被拒绝的比例。
- mutating action 审批卡里，人类需要补充信息的比例。
- rerun 后 RC=0 的比例。
- 凭证、hidden field、production data 是否被正确隔离和脱敏。
- 团队是否愿意把 Hopper 放进日常 runbook，而不只是试一次。

## 商业化路径

1. **个人 / hobby 免费。** 让 mainframe 爱好者、学生、咨询顾问先试。
2. **团队版。** 共享 workspace、任务历史、审批记录、runbook template、标准 job debugging workflow。
3. **企业版。** SAML SSO、admin controls、org-wide privacy controls、no model training、SOC 2 / pen test、审计导出。
4. **私有部署 / VPC / on-prem。** 对银行、保险、政府、航空这类客户，部署方式就是销售门槛。
5. **咨询交付工具。** 给 mainframe modernization 厂商做交付加速器：新人培训、排障、迁移前资产理解。

## 反例 / 风险

1. **生产信任很难。** 企业可以接受 agent 读和解释，但让它写 PDS、submit JCL、碰 CICS，需要很长信任爬坡。
2. **数据安全要求重。** VSAM snapshot、logs、tap data、chat context 都可能含敏感信息。只要泄一次，产品就很难翻身。
3. **客户销售慢。** Mainframe 客户预算真，但采购、安全评审、部署和合规会拖很久。
4. **专家可能不买账。** 资深 mainframe 工程师如果觉得 agent 解释不准、审批卡不够细，会直接弃用。
5. **大厂和存量供应商会追。** IBM、Broadcom、BMC、Rocket Software、主流 AIOps/DevTool 厂商都有切入理由。独立公司的优势必须是体验、速度和跨工具 agent workflow。
6. **MVP 容易被 demo 骗。** 一个 sandbox 里的好看 demo 不代表生产环境能用。要看真实脏数据、老命名、奇怪 JCL、权限限制、非标准 runbook。

## 我的判断

Hopper 是值得继续跟踪的垂直 AI 项目。

它的好处是切口硬：任务对象明确、用户痛点旧且贵、AI 压缩链条具体、付费人清楚。它的问题也硬：安全、合规、生产信任、采购周期、专家认可，一个都绕不过去。

最该跟的不是 HN points，而是三件事：

- 是否能拿到真实 enterprise / consulting design partners。
- 用户是否从只读诊断走到批准 mutating actions。
- Hopper 能不能沉淀 mainframe workflow template，而不是只做一个聊天面板。

## 后续跟踪点

- Enterprise 版是否公开 design partner、case study 或合规材料。
- mutating action approval 是否能做到足够细，尤其是 JCL class、CICS install、bulk deploy。
- 是否支持更多模型和私有模型，而不是只依赖单一云模型。
- 是否出现 mainframe workflow template / runbook marketplace。
- 资深 mainframe 工程师在真实项目中是把它当助手，还是当风险源。
