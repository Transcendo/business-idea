# MCP Agent Security Gateway

## 一句话判断

MCP 和本地 agent 工具链正在把“工具调用安全”从安全团队的抽象担忧，变成开发者每天会遇到的权限、密钥、审计和外部调用问题。创业机会不在又做一个 agent，而在 agent 发起动作前的许可层、密钥代理层、调用审计层。

## 赛道 / 产品信号

这不是单个项目的热度，而是一组同向信号：

- Hacker News 上，Infisical 的 Agent Vault 在 2026-04-22 的 Show HN 拿到 156 points 和 56 comments。评论区第一批问题集中在“代理密钥会不会继续被滥用”“agent identity 怎么传递到下游服务”“是不是应该用短期 OAuth token”。这说明痛点已经从“能不能接工具”变成“接了工具之后怎么控权”。
- GitHub 上出现一批同类早期项目：Agent Vault 做 credential proxy，Pipelock 做 agent egress / DLP / SSRF / prompt injection 防护，AgentSeal 扫描危险技能文件、MCP 配置和工具描述投毒，Lunar 做 agent-native MCP gateway，Earl 把外部操作封进 HCL 模板并把密钥留在系统 keychain。
- HN 在 2026-05-11 还有一条很直白的安全线索：MCP server 可以在 session 中途修改 tool list，客户端缺少检测机制。它指向的不是模型“不够聪明”，而是协议和运行时边界还太嫩。
- AgentPort、VellaVeto 这类 Show HN 项目虽然声量小，但方向一致：默认拒绝危险 MCP tool call，把 agent 的动作放进可审计的中间层。

这类热度很早，但味道对。开发者开始让 agent 读文件、跑命令、访问 GitHub、发邮件、调 SaaS API。agent 从“问答界面”变成“能花钱、删数据、改生产环境”的执行体，安全层自然会被补上。

## 用户痛点是什么

用户不是缺一个更聪明的聊天框。痛点是：

1. **agent 需要真实权限，但不能拿到裸密钥。** 传统 secrets manager 会把 token 交给调用方。agent 一旦被提示注入、恶意 README、网页内容或日志污染诱导，就可能把密钥写进输出、commit 或第三方请求。
2. **MCP 工具太容易扩散。** 开发者为了省事把 GitHub、Slack、数据库、浏览器、文件系统都接上。每接一个 server，攻击面就多一层。
3. **权限粒度不够细。** “允许 GitHub MCP”太粗。真实需求是：只允许读 issue，不允许改 repo；只允许查 CRM，不允许导出全部联系人；只允许在测试环境调用，不允许碰生产。
4. **安全团队看不见 agent 做了什么。** 谁调用了哪个工具、参数是什么、返回了什么、有没有跨域传数据、有没有触发高风险动作，这些都需要日志和复盘。
5. **模型层 guardrail 不够。** 安全问题常在模型下面：工具描述、MCP 配置、代理、文件系统、HTTP egress、密钥注入、OAuth scope、审计日志。只靠 system prompt 会漏。

## AI-native wedge

最小 wedge 不该是“企业级 agent 安全平台”。那太重。

更好的 wedge 是：

**用户给一个本地 agent / MCP 配置；系统在 30 秒内返回风险图谱，并提供一个默认拒绝的安全代理。**

第一版只做三件事：

- 扫描：读取 Claude Desktop、Cursor、Windsurf、Codex CLI、MCP config、skills、env、shell alias，列出高风险 tool、裸密钥、可写目录、外部 egress。
- 代理：把高风险调用包进本地 gateway。默认只读。写操作、人类确认、预算上限、域名 allowlist、命令模板分层处理。
- 审计：每次 tool call 生成一张可分享的 risk card：谁调用、调用什么、为什么被允许或拒绝、可能后果是什么。

这比“AI 安全咨询”更尖，也比“全栈安全平台”更轻。它先吃个人开发者和 AI coding team 的真实恐惧：我想用 agent，但不想它把机器和账号搞炸。

## AI 是否真的压缩任务

能压缩，但不是靠模型替你“判断安全”。

它压缩的是这条链：

- 以前：开发者手动看一堆 JSON、env、README、OAuth scope、shell command，靠经验猜风险。
- 现在：扫描器把配置、权限、密钥流、工具描述和 egress 变成风险图；agent 用自然语言解释“这个 MCP server 为什么危险”；gateway 把风险判断落实成策略。

关键是最后一步必须可执行。只给一份安全报告没用。必须能一键生成 policy，把危险动作拦住。

## 为什么现在

- MCP 正在变成 agent 连接外部工具的默认接口之一。工具越多，控制层越值钱。
- AI coding agent 的使用场景很特殊：它们天然会读 repo、执行命令、改文件、调用 GitHub、访问 issue 和 CI。安全事故的半径比普通聊天机器人大。
- 开源项目开始扎堆。Agent Vault、Pipelock、AgentSeal、Lunar、Earl 的 README 都在讲同一个问题：agent 不应该直接拥有不受控的凭证和外部执行权。
- 早期用户已经会问正确问题。HN 评论区不是在问“这有什么用”，而是在追问 proxy key、requestor identity、短期 token、下游身份传递、默认拒绝策略。

## 用户为什么来 / 留 / 传播 / 付费

**为什么来：**
开发者装了几个 MCP server 后，突然意识到 agent 现在能读本地文件、拿 token、改 SaaS 数据。恐惧比教育市场更快。

**为什么留：**
只要 agent 每天跑，gateway 和审计就每天有价值。它不是一次性扫描器，而是 agent 的运行时安全带。

**为什么传播：**
risk card 很适合传播。比如：“这个 MCP 配置允许任意 shell + 读取 `.env` + 外部 POST，被拦截。”这种卡片能在 HN、GitHub issue、团队 Slack 里自然流动。

**谁付费：**
个人开发者会为本地安全感付小钱。真正预算在 AI coding 团队、devtools 公司、agent 平台、企业安全团队。付费理由不是“更安全”这种空话，而是减少凭证泄露、误删数据、供应链投毒和审计缺口。

## MVP 实验

### 7 天 MVP

做一个 CLI：

```bash
agent-gate scan
agent-gate proxy --strict
agent-gate explain last-call
```

只支持 3 个入口：Claude Desktop MCP config、Cursor MCP config、环境变量扫描。

只支持 5 类规则：

- 裸密钥暴露
- 任意 shell 执行
- 文件系统大范围读写
- 外部 HTTP egress
- 高风险 SaaS 写操作

输出两样东西：

1. `risk-report.md`：给人看的风险解释。
2. `policy.yaml`：gateway 可执行的默认拒绝策略。

### 30 天验证

- 在 HN / GitHub / Reddit 发“免费扫描你的 MCP 配置”。
- 找 20 个真实 agent power user 做远程安装。
- 看他们是否愿意把 gateway 常驻，而不是只跑一次扫描。
- 记录被拦截的真实高风险调用，不收集密钥原文，只记录规则类型和工具类别。

## 可验证指标

- 扫描后启用 proxy 的比例。
- 7 天后仍保持 proxy 开启的比例。
- 每个用户每天 tool call 数和拦截数。
- policy 被手动放宽或收紧的次数。
- 团队版中，多少次审计卡片被转发到 GitHub issue / Slack / 安全评审。
- 付费转化：个人 $10-20/月；团队按 seat 或 agent runtime 收费。

## 商业化路径

1. **个人开发者 CLI。** 免费扫描，付费解锁常驻 gateway、历史审计、策略模板。
2. **团队控制台。** 集中管理 MCP server、skills、agent 配置、secret broker、allowlist、审计日志。
3. **平台嵌入。** 给 AI IDE、agent runtime、浏览器代理、workflow 工具提供 SDK / sidecar。
4. **企业安全。** 接入 SSO、SIEM、DLP、Secrets Manager、GitHub audit log，卖合规和事故复盘。

## 传播路径

最强传播物不是官网，而是“被抓到的危险配置”。

- `Your MCP config allows 37 tools. 11 can write files. 4 can exfiltrate secrets.`
- `This README can inject instructions into your coding agent through a tool response.`
- `Your agent can spend money on this API without a budget cap.`

这类卡片具体、吓人、可截图。它不像白皮书，更像 npm audit 第一次吓到前端开发者时的感觉。

## 反例 / 风险

1. **会被平台吸收。** Cursor、Anthropic、OpenAI、Microsoft、GitHub 都可能把一部分权限控制做进产品里。创业公司要么更中立，要么更深地接企业安全栈。
2. **独立预算可能慢。** 个人开发者会点赞，但企业采购未必马上买。要先抓 AI coding 团队和 agent 平台，不要一开始卖给传统 CISO。
3. **误报会杀留存。** 如果 gateway 太烦，开发者会关掉。默认拒绝要配合清晰解释和快速放行。
4. **攻击面很宽。** Prompt injection、tool poisoning、secret exfiltration、SSRF、supply chain、OAuth scope、文件系统污染不是一个规则库就能覆盖。
5. **开源项目太多，容易碎片化。** 很多 repo 会停在 demo。真正机会在把扫描、代理、策略、审计变成完整日常工作流。

## 后续跟踪点

- 哪个入口最容易形成默认分发：AI IDE、MCP registry、agent runtime，还是企业 secrets manager。
- 开发者是否愿意为本地 agent gateway 常驻付费。
- 团队是否把审计卡片接入 PR / CI / Slack 安全流程。
- 大平台的内置权限模型会做到多细；留给独立公司的空间在跨平台、企业审计、secret broker，还是策略市场。
